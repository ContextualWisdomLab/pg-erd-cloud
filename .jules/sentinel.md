## 2025-02-18 - Hardening Pydantic String Fields Against Control Characters
**Vulnerability:** User-provided string fields (like project and connection names) lacked strict validation against control characters, only relying on length constraints.
**Learning:** This could potentially lead to Log Injection (CRLF injection), Null Byte Injection, or terminal escape injection if these strings are subsequently logged or rendered directly.
**Prevention:** Use explicit regex validation `pattern=r'^[^\x00-\x1F\x7F]+$'` on Pydantic string fields to strictly reject control characters.

## 2025-02-23 - URL Encoded Password Handling in DSN Redaction
**Vulnerability:** URL-encoded passwords and query parameters inside connection DSN strings could bypass the driver error message redaction logic. Short secrets were also subject to severe over-redaction if not bounded by words.
**Learning:** `urllib.parse.urlsplit().password` and query parameter parsing returns strings that might still be partially encoded or differently encoded than the raw error message string generated by underlying database drivers. Blindly substituting short secrets everywhere in an error message string corrupts legitimate content (e.g. `password` becomes `***word` if the secret is `pass`).
**Prevention:** Explicitly decode parsed URL components (using `unquote_plus`) and generate all potential variations of the secret (`unquote_plus`, `quote`, `quote_plus`) to ensure the redaction mechanism matches whatever specific encoding the database driver emits in its logs. When redacting, use regular expression word boundaries `(?<![A-Za-z0-9]){re.escape(secret)}(?![A-Za-z0-9])` specifically for short secrets (<= 4 chars) to prevent corrupting larger words while still ensuring they are scrubbed, while unconditionally replacing longer secrets.
