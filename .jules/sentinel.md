## 2025-02-18 - Hardening Pydantic String Fields Against Control Characters
**Vulnerability:** User-provided string fields (like project and connection names) lacked strict validation against control characters, only relying on length constraints.
**Learning:** This could potentially lead to Log Injection (CRLF injection), Null Byte Injection, or terminal escape injection if these strings are subsequently logged or rendered directly.
**Prevention:** Use explicit regex validation `pattern=r'^[^\x00-\x1F\x7F]+$'` on Pydantic string fields to strictly reject control characters.
## 2026-08-04 - Remove the vulnerable python-ecdsa dependency from JWT verification
**Vulnerability:** `python-jose[cryptography]` introduced the `ecdsa` package, which remains affected by the Minerva P-256 timing side-channel advisory (CVE-2024-23342 / GHSA-wj6h-64fc-37mp / PYSEC-2026-1325) with no planned upstream side-channel fix. The issue is the dependency path, not an unsupported claim that `python-jose` has no maintainers.
**Learning:** `PyJWT[crypto]` avoids that pure-Python ECDSA dependency for this OIDC path, but its API differs from `python-jose`: `jwt.decode` receives `jwt.PyJWK(jwk).key`, required claims use the `options["require"]` list, leeway is a top-level argument, and verification exceptions inherit from `jwt.PyJWTError`.
**Prevention:** Keep a fixed application-controlled algorithm allowlist, require issuer/expiration/token identifier and the configured audience, regenerate hash-locked requirements, and test the library-specific key, claim, leeway, and exception contracts. The authoritative standards and APA 7 references are recorded in `docs/doctoring/jwt-verification-and-library-migration.md`.
